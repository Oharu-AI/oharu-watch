# 日本・アジア媒体、アクセシビリティ、反証：調査結果

確認日: **2026-08-23（日本時間）**
担当: 日本・アジアのニュース設計、アクセシビリティ、反証

## 要約

日本・アジアの媒体に共通していたのは、見た目の模倣ではなく「最初に何を読ませるか」を固定する情報階層（リード、速報・新着、ランキング、カテゴリ）と、スマホでの保存・通知・地域選択などの再訪導線である。ITmedia NEWS と日経の公開トップ相当ページは、日本語の長い見出しを時刻・ラベル付きのリストへ整理しており、画像を大きく使う SCMP や Nikkei Asia は、写真・動画・インフォグラフィックを前提にした別の商品設計である。OHARU WATCH は直近7日・306件（2026-08-23のローカルデータ）を扱い、通常運用では画像不足と静的HTMLという制約があるため、世界的サイトをそのまま真似るより、テキスト主体の安定した行リズム、カテゴリ移動、段階表示を優先するのが安全である。WCAG 2.2 の4.5:1コントラスト、可視フォーカス、24×24 CSS px以上のポインター対象と、web.devの実用的な48×48px目安、Core Web Vitals（LCP 2.5秒、INP 200ms、CLS 0.1）を次期案の受入基準にできる。

## 調査方法と限界

- 以下のページを検索結果から開き、本文・見出し・リンク構造を確認した。確認日はすべて2026-08-23。ページ本文の取得結果を根拠にしており、検索スニペットだけの主張はその旨を明記した。

## アクセシビリティ根拠

### 規格・一次資料

- [WCAG 2.2（W3C）](https://www.w3.org/TR/WCAG22/) 1.4.3（Level AA）は通常テキスト4.5:1以上、大きな文字3:1以上のコントラストを要求する。1.4.4はテキストを200%まで拡大しても内容・機能を失わないことを要求する。
- 同じWCAG 2.2の1.4.8（Level AAA）は、視覚的な本文の幅を80文字以下（CJKは40字以下）にし、両端揃えを避け、段落内行間を少なくとも1.5倍にする選択肢を示す。AA必須条件ではないが、OHARU WATCHの記事詳細の読みやすさを評価する有力な目安である。
- WCAG 2.2の2.4.7（AA）はキーボード操作時にフォーカス表示が見えること、2.4.11（AA）は固定ヘッダー等でフォーカス対象が完全に隠れないことを求める。2.4.13（AAA）はフォーカス表示の2 CSS px相当の面積と、状態間3:1以上のコントラストを示す。
- WCAG 2.2の2.5.8（AA）はポインター対象を原則24×24 CSS px以上とする（間隔・インライン等の例外あり）。[web.dev「Accessible tap targets」](https://web.dev/articles/accessible-tap-targets?hl=en) は、モバイルの実用的な最小推奨として48 device-independent px程度（約9mm）を示す。したがって、法的なAA判定は24px、ニュースのカテゴリボタンや「さらに表示」は誤タップ防止のため48px近辺を目標にする。
- [web.dev Web Vitals](https://web.dev/articles/vitals?hl=en) は、良好な体験の目安をLCP 2.5秒以内、INP 200ms以下、CLS 0.1以下とし、モバイル／デスクトップ別に75パーセンタイルで測るよう説明する。[CLSの解説](https://web.dev/articles/cls?hl=en) は、遅れて画像が入る等の予期しない移動が誤タップや読書位置喪失を起こすと説明している。

### 現行OHARU WATCHへの照合

`style.css`を読み、ローカル計算も行った（サイト自体の画面テストではない）。現状の良い点は、本文16px・行高1.7、`a:focus-visible`／`button:focus-visible` の3pxアウトライン、詳細ページの出典ボタン最小48px、追加表示ボタン最小46px、画像の`aspect-ratio`指定である。これらは基準に近い。

改善候補は次のとおり。

1. モバイルのカテゴリリンクは12px文字＋上下7pxのため、継承行高を含めてもおよそ34px。WCAGの24pxは満たし得るが、web.devの48px実用目安には届かない。リンク自体の上下余白を増やすか、カテゴリナビの行高を48px近くにし、隣接対象の間隔を確保する。
2. `--muted`の`#667085`は白地とのコントラストが約4.97:1でAAを満たす一方、`source-name`の`#778396`は白地とのコントラストが約3.84:1で、通常サイズの本文としては4.5:1を下回る。媒体名が情報として必要なら色を濃くする（または文字サイズを大きな文字扱いにしない）方が安全である。
3. 固定ヘッダーとページ内アンカーの組み合わせは、フォーカス対象をヘッダーの下に隠す可能性がある。`scroll-padding-top`だけに依存せず、キーボードTab操作でフォーカス枠が見えることを確認する。
4. 画像は遅延読み込みでも、枠の高さを常に確保する。既定画像への切り替えで異なる比率を混ぜない。これがCLSを抑え、読み込み後に記事の縦位置が動くのを防ぐ。
5. 記事詳細では本文の最大幅を40字程度のCJK相当へ近づける選択肢を検証する。900pxの外枠いっぱいに長文を置くと、文字サイズによってはWCAG 1.4.8の80字／CJK40字目安を超えるため、本文だけ`max-width`を持たせ、見出し・画像は広く保つ構成がよい。

## OHARU WATCHへの提案

優先順位は「似た見た目」ではなく、次の順にする。

1. **静的HTMLのまま、リード1件＋カテゴリ別リストを維持する。** ITmedia／日経の共通点であるリードと時系列の分離を採用し、通常記事のタイトル・媒体・時刻・本文抜粋を同じ順序で反復する。画像は補助要素とし、画像なしでも意味が通る。
2. **カテゴリナビを目的語にする。** 現在の4分類（国内AI、国外AI、Apple公式、Appleリーク）は維持しつつ、見出しの近くに件数と「先頭30件／さらに20件」を明記する。Nikkei Asiaの企画名のように、将来追加する場合も「今日の要点」「公式発表」「うわさ・リーク」の読み方が一目で分かる名前にする。
3. **縦リズムを固定する。** リード以外は画像112〜176px相当の一列カードで、タイトル最大3行、メタデータ1行、本文抜粋はデスクトップのみとする現行方針を基本にする。カードごとの大きな影・丸角を増やさず、薄い境界線と24px前後のセクション間隔で連続読書を優先する。
4. **スマホの操作面を先に決める。** カテゴリリンク、「続きを読む」、「さらに表示」、外部記事リンクは最低44〜48pxの高さを目標にする。横スクロールナビにはキーボードで移動できるリンク、見切れがある場合の視覚的な続きがあることを示す手がかり、現在カテゴリの色以外の選択状態（下線や`aria-current`）を用意する。
5. **速度をデザイン要件に含める。** `articles.json`を巨大な見た目のカードへ一括変換せず、初期表示30件に画像遅延読み込みを限定する。LCPはリードのテキスト／既定画像を2.5秒以内、カテゴリ追加ボタンはINP 200ms以下、画像領域確保でCLS 0.1以下を目標にする。実測は公開後のPageSpeed InsightsまたはChrome DevToolsで行う。
6. **アクセシビリティを受入テストにする。** 200%ズーム、Tabキーでのフォーカス、フォーカス枠と固定ヘッダーの重なり、白地の媒体名コントラスト、375px幅での横はみ出し0を毎回確認する。画像が既定画像でもタイトルとリンクが一意に読めることを確認する。

## 反証・リスク（「世界的サイトを真似ればよい」への反論）

- **商品条件が違う。** SCMPやNikkei Asiaは、写真・動画・インフォグラフィック、編集部の企画、アプリ通知、検索・アーカイブ、購読／法人読者を含む事業である。画像と記事の制作量を前提にした大きなヒーローや雑誌風グリッドを、OGP画像が取れない静的個人サイトへ移すと、同じ既定画像の反復と大きな空白が目立つ。
- **日本語は英語の幅の換算にならない。** 英語サイトの「3行カード」を日本語にそのまま適用すると、長い固有名詞・全角記号・英数字の混在で行数が跳ねる。文字数上限だけで切ると意味が失われるため、2〜3行の`line-clamp`、タイトルの優先語、媒体・時刻の分離を端末で確認する必要がある。
- **大量記事では「美しい密度」が過密になる。** 現在のローカルデータは306件で、国内AI167、国外AI112、Apple公式13、Appleリーク14。世界的大手のトップページにある十数件の編集済みリードと違い、OHARU WATCHでは同じ視覚的強調を306件へ適用すると重要度の差が消える。初期表示と追加表示を分け、カテゴリごとの件数を可視化する方が非エンジニア読者に説明しやすい。
- **ランキングやおすすめは重複・偏りを生む。** ITmediaのようなランキングは発見性を高めるが、OHARU WATCHではおすすめ記事と通常カテゴリの重複、RSS媒体の偏り、リーク記事の過剰な視覚強調を招く。ランキングを新設する場合はIDで通常リストから除外し、選定理由を短く示す。
- **AIタイトルの不確実性を装飾で隠してはいけない。** 大きなリード画像・強い色・「重要」バッジは、RSSの抜粋や翻訳タイトルの確度以上に信頼できる印象を与える。媒体名、原文リンク、公開時刻、必要なら「リーク」「公式」のラベルを先に見せる。
- **災害向け設計は用途が異なる。** NHKの速報・避難・地図・通知は命に関わる情報のための優先順位である。AI／Appleニュースの通常フィードへ赤い速報帯や点滅を常用すると、緊急性の基準が崩れる。速報表示を採用する場合も、実際に緊急情報があるときだけ出す。
- **静的サイトでは機能の借用範囲が違う。** SCMPのAI検索、Nikkei Asiaの通知、NHKの地域マップは、サーバー・アプリ・継続運用が前提。OHARU WATCHでは同じ機能ではなく、検索リンク、カテゴリアンカー、保存しやすいURL、軽量な追加表示へ翻訳する。

## 見つからなかったこと

- `www3.nhk.or.jp/news/`、`news.web.nhk/newsweb`、`www.nikkei.com/`、`asia.nikkei.com/`の通常トップ、`www.scmp.com/`本体は、robots.txtまたは403で取得できず、現在のCSS、画面スクリーンショット、正確な見出しの折返しを確認できなかった。
- 朝日新聞デジタルの現行記事一覧も直接確認できず、現行画面の文字サイズ・罫線・スマホUIは断定していない。確認できた公式PDFは2020年版のため、現行UIの根拠にしない。
- いずれの媒体についても、媒体側の内部A/Bテスト、記事カードの実際のフォントCSS、モバイルでの平均読了率は公開本文から確認できなかった。SCMPの改善率を含む第三者記事は検索で見つかったが、今回の主張は公式告知と直接確認できた媒体本文に限定した。
- OHARU WATCHの次期デザインが読了率・再訪率を改善するという因果は、アクセス解析や比較試験なしには言えない。現時点の提案は、WCAG・速度・既存の静的制約に適合しやすい仮説である。
